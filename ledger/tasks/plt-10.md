# Parent-owned endpoint identity

Delivered, not complete. The launch-identity library is merged. It was built and tested offline in hosted Linux CI (`managed-packages / pack`, ubuntu-24.04) and built and tested on Windows locally by the claimant and by the reviewer, including three opt-in real-process checks; no hosted job builds `ArcForges.LocalRpc` on Windows (the Windows jobs build native code and the PRF.04 probe). The task's own completion evidence has four scenarios and they are not equally observed. Concurrent launch and parent-death cleanup were observed with real processes, on Windows only and through the Unix-socket route (AF_UNIX on Windows, with a launch directory and a socket), not through the shipped Windows endpoint (a Named Pipe with an unguessable name and no file). Stale descriptor was observed with a real killed parent (a new authority refused the old descriptor's claim and the old launch reported a parent mismatch) and in offline fixtures. Forged nonce and forged build were observed only in offline fixtures with a fake process table and clock, never with an OS process. The Unix launch-directory path, which is the shipped endpoint on Linux and macOS, and the Linux `/proc` process identity ran only in hosted offline tests that start no real parent and kill none; nothing ran on macOS. The task has no completion prerequisite in the graph, so it opens as a completion follow-up (DLV-41) for a worker with Linux and macOS hosts and a second OS account.

## Untested coverage

- **Wrong-user and cross-account denial: never observed.** No second account was available. Only the access-control and mode requirements were checked.
- **The Windows root-ownership check** (the owner must be the current user or Administrators) has no test: it needs a directory owned by another account (mutants of it survived by design). The Unix root check is mode-only with no ownership check, so a root parent is not covered.
- **Peer OS identity is not read or authenticated.** A same-user process that learns an endpoint address can connect; the nonce and the one-use secret decide what a claim may do, and the proof that uses the secret is PLT.11's. Reading the Windows pipe client PID needs a native binding the repository restricts; for launcher-supplied streams the OS names the creating parent, not the child.
- **The Named Pipe is reachable through the network namespace** (for example `\\127.0.0.1\pipe\<name>`), inherited from PLT.09; not claimed to be network-isolated.
- **Linux and macOS real-process runs: not performed.** The Unix launch-directory path ran only in hosted Linux offline tests (owner-only modes, sweep) with no real parent started or killed; the Linux `/proc` start-tick read ran only in hosted CI (a self-probe plus parser unit tests) and never locally; macOS has no host and no CI. The three opt-in process checks are Windows evidence only.
- **Pid and tick reuse across a reboot** is not exercised: a record from before a reboot whose process id and start tick coincide with a running process would be taken as that process, and its directory kept, never deleted (fails safe, by reasoning).
- **A callback that returns a rejected proof still ends the bootstrap window**, because `ConsumeSecret` does not interpret its result; PLT.11 must revoke the launch on a rejected proof.
- **Repeatability of the real-process checks is not measured.** The PLT.09 residual AF_UNIX-on-Windows flake (reviewer-reported in PLT.09's record: 2 failures in 250 full opt-in runs, cause not found) was not investigated here, yet the concurrent-launch and orphan checks use that route on Windows; the claimant ran the opt-in suite once on the merged head (the claimant reports that earlier heads also passed in single runs; no log is stored), so no clean-run count is claimed.
- **A silent admitted peer still holds a connection slot** (only the connection decision is bounded here); PLT.13 owns that bound.
- **Native AOT publish of `ArcForges.LocalRpc`:** not performed; static AOT and trim analyzers pass, and no CI job compiles this library.
- **Guard paths not reached by a test:** the disposed-race `catch` in `Revoke` (a race between two threads); a record that is not understood is kept forever (no cleanup path); the retry give-up and `Remove` fallback paths are checked only on Windows with a held handle.
- **Memory handling:** the secret is zeroed in managed memory only; it is not pinned or locked and the handoff array's clearing is the launcher's job.
- **Not in scope and not claimed:** registration lease, renewal and epoch fencing of registrations and the LocalBootstrap proof (PLT.11), routing and version refusal (PLT.12), call bounds (PLT.13), disconnect and retry (PLT.14), brokered resources (PLT.15), package publication (PLT.16), restricted-launch containment (PLT.45).
